## 2. Decisões de setup (MCP / tooling)

| ID | Decisão | Justificativa |
|---|---|---|
| **D-01** | Pacote Unity fixado em `v10.2.0` | `main` do repositório é instável. `v10.2.0` é a última release estável e casa com o `mcpforunityserver==10.2.0` do PyPI. |
| **D-02** | Config do MCP escrita **manualmente** em `opencode.json`, nunca pelo botão "Configure" do plugin | O `OpenCodeConfigurator.cs` do plugin escreve `mcp.unityMCP` — formato **V1**. O OpenCode **V2** usa `mcp.servers.<nome>`. Usar o botão sobrescreveria a config com algo que o V2 ignora silenciosamente. |
| **D-03** | `opencode.json` na **raiz do projeto** (escopo local) e não global | Escolha do usuário. Server detecta a instância do Unity automaticamente. |
| **D-04** | `/opencode.json` adicionado ao `.gitignore` | A config contém caminho absoluto da máquina (`C:\Users\Igor\...`), não deve ir para o repo. |
| **D-05** | `timeout.startup = 120000` no server MCP | O primeiro `uvx` baixa o pacote do PyPI; o default de 30 s estoura. |
| **D-06** | Transporte **stdio** (não HTTP) | O `StdioBridgeHost` do plugin abre a porta 6400 e o server conecta de volta. Verificado: `DefaultPort = 6400` em `PortManager.cs`. |
| **D-07** | Transporte configurado via `uvx` com **caminho absoluto** | `AssetPathUtility.GetUvxCommandParts()` do plugin também usa caminho absoluto; independe do PATH do shell. |

## 3. Decisões de design (narrativa e jogabilidade)

**Conceito:** *PROTOCOLO CÉLULA-9* — você é o último técnico de plantão da Filial 9 do
Banco Ártico, agência 100% automatizada que foi desativada no meio de uma falha de
energia. O terminal de autoatendimento é a única máquina ainda com carga e o único
canal de saída.

| ID | Decisão | Justificativa |
|---|---|---|
| **D-08** | Puzzle do **crachá de turno** como portão dos itens | O jogador precisa *deduzir* um símbolo cruzando duas fontes no ambiente (mural de plantão + registro de manutenção com timestamp 02:47), em vez de só coletar. Atende "coloque algo para o jogador pensar". |
| **D-09** | Sem game over no puzzle; erro só dá feedback sonoro + `CREDENCIAL RECUSADA` | Punição num screencast de 5 min arrisca travar a demonstração. O feedback ensina sem frustração. |
| **D-10** | **Segundo momento de dedução:** ordem de inserção dos itens | Terminal mostra `PROTOCOLO: ____ → CÉLULA → AUTORIZADO` (texto danificado). O jogador raciocina que a chave vem antes, porque a célula não tem energia para acionar o leitor. Erro devolve o item com som **distinto** do de credencial — o jogador aprende pela diferença. |
| **D-11** *(áudio, ver também §4)* | Trilha e SFX **sintetizados por script Python** | O projeto não tem nenhum asset de áudio além de passos. Sintetizar elimina custo de licença e de download, e dá controle fino. Ver `Assets/EscapeRoom/Audio/generate_audio.py`. |
| **D-12** | Cronômetro **"RESERVA CRÍTICA"** de 6:00, diegético | O tempo **é a bateria do terminal** — a única carga restante. Não é um relógio arbitrário. |
| **D-13** | O cronômetro ** só começa ao clicar em FORÇAR REINÍCIO** | Explorar e ler o mural é grátis. Isso recompensa a exploração em vez de punir, e a pressão passa a incidir sobre a dedução — que é justamente o que deve ser pressionado. |
| **D-14** | Estado de falha **reaproveita o mesmo botão** da UI (`REINICIAR`) | O requisito de UI pede ≥1 botão com `OnClick`. Assim o botão tem **dois estados funcionais reais** em vez de ser enfeite — e o fail state é diegético (magneto-travas reengatam). |

## 4. Decisões técnicas

| ID | Decisão | Justificativa / evidência |
|---|---|---|
| **D-15** | **1ª pessoa**, não 3ª pessoa | A cena já tinha `FirstPersonController` no capsule mas um rig `CinemachineThirdPersonFollow` na câmera — **conflito**: rotação dupla (mouse gira o corpo *e* a câmera segue), avatar visível, e o raycast de grab sai torto do centro da tela. FPS resolve mira central + imersão + deixa a Canvas World Space legível de frente. **Aprovado explicitamente pelo usuário.** |
| **D-16** | **Não remover o Cinemachine** ao corrigir a câmera | `FirstPersonController.cs:147` faz `CinemachineCameraTarget.transform.localRotation = ...` **sem guarda de null**. Tirar o Cinemachine geraria `NullReferenceException`. Solução: manter o rig e zerar o offset do follow. |
| **D-17** | Agarrar/inserir por **clique com raycast da câmera** | Escolha do usuário ("interagindo por cima do terminal — o item voa pro slot ao clicar"). Mais fácil de gravar. |
| **D-18** | Decisão final: **tela de vitória com cronômetro** | Escolha do usuário. Entrega "meta cumprida" de forma visível no vídeo. |
| **D-19** | **UI com `UnityEngine.UI.Text` legado**, não TextMeshPro | **TMP não tem os Essential Resources importados** no projeto (não existe `Assets/TextMesh Pro/`). Sem o font asset padrão, TMP erra em runtime. `Text` + `Resources.GetBuiltinResource<Font>("LegacyRuntime.ttf")` funciona sem nenhum import. Escolha de **menor risco e retrabalho zero**. |
| **D-20** | EventSystem com **`InputSystemUIInputModule`** | O projeto está em `activeInputHandler: 1`. Um Canvas com `StandaloneInputModule` **não recebe clique nenhum** — o botão morre sem erro visível. Este é o ponto que mais derruba esse tipo de projeto. **A cena não tinha nenhum EventSystem nem Canvas** (verificado por busca no `.unity`). |
| **D-21** | Cursor **travado** e raycast de UI pelo centro da tela | `GraphicRaycaster` usa a posição do ponteiro, que com o cursor travado é o centro da tela. Permite clicar nos botões da Canvas World Space sem desbloquear o mouse. |
| **D-22** | Slots de inserção são **objetos 3D separados** da Canvas | A Canvas fica na parte de cima do terminal; os slots ficam abaixo, com colliders próprios. Isso **elimina qualquer conflito de clique** entre UI e raycast de mundo. |
| **D-23** | Materiais criados **em runtime** via `Shader.Find("Universal Render Pipeline/Lit")` | `Shader.Find` + `Material` é 100% previsível; evita dezenas de chamadas de MCP só para setar shader e propriedades. Degrada com segurança via `HasProperty`. |
| **D-24** | Geometria do set **construída em tempo de edição** por script de editor com `[MenuItem]`, não em runtime | Se fosse em runtime, os objetos **não existiriam no arquivo `.unity`** — a cena salva ficaria vazia para quem avalia. Construindo em edição, tudo fica salvo e versionado. |
| **D-25** | Nenhum `PlayerController` novo | O `FirstPersonController` do Starter Assets já cobre locomoção, sprint, jump, crouch, head bob e passos. Escrever outro seria retrabalho. |
| **D-26** | A ação `Interact` **não** foi adicionada ao `.inputactions` | As ações disponíveis são só `Move/Look/Jump/Sprint`. Para evitar regenerar o wrapper C# e mexer em asset de terceiros, os scripts leem `Keyboard.current` / `Mouse.current` diretamente (API do Input System, não a antiga `Input.GetKey`). |
| **D-27** | Toda chamada de tool do Unity é **sequencial**, nunca `Promise.all` | Descoberto empiricamente: duas tool calls paralelas falham com `No Unity Editor instances found` — corrida na seleção de instância do servidor. Em sequência, funciona. |
| **D-28** | Cena vazia sem nome foi salva em `Assets/Temp/_scratch_empty.unity` antes de trocar de cena | `manage_scene load` recusa se há alterações não salvas. Evitei `File > New Scene` / `close_scene` de propósito: um **modal** travaria a main thread do Unity e mataria a ponte MCP. O arquivo foi removido logo em seguida. |
| **D-29** | O `OnClick` é registrado em **runtime** (`btn.onClick.AddListener`) no `TerminalController.Start()`, não como listener persistente | Um `UnityEventTools.AddPersistentListener` no editor exigiria acertar a API de `UnityEvent` genérico sem poder compilar-fail-corrigir rapidamente. `AddListener` em runtime é um `OnClick` real e idêntico em comportamento. **Verificado**: `SelfTest 1` mostra `persistent listeners = 0` e mesmo assim `Invoke()` leva a fase de `Offline` para `Booting`. |
| **D-30** | Câmera em 1ª pessoa por script próprio (`EsFirstPersonCameraRig`), removendo o `CinemachineBrain` | Alternativa seria reescrever o follow do Cinemachine 3 com offsets zerados, cuja API muda entre versões. Copiar a pose do pivô no `LateUpdate` reproduz o comportamento de FPS com 10 linhas e zero dependência de API versionada. O pivô `CinemachineCameraTarget` continua existindo, então a linha 147 do `FirstPersonController` não toma NRE. |
| **D-31** | A regra de ordem (chave antes da célula) é um **guard** avaliado *antes* do item ser consumido | Versão inicial validava a fase no callback `onFilled`, ou seja **depois** de o socket já ter engolido o item — o jogador perdia a mão. `ItemSocket.guard` (um `Func<GrabbableItem,bool>`) faz o veto acontecer antes, e o `bool Interact()` devolve `false` para o item ficar na mão. **Verificado** por `SelfTest 4`. |
| **D-32** | O locker é uma **cavidade de 5 painéis** (fundo, laterais, teto, prateleira), não uma caixa sólida | Com caixa sólida os itens ficariam presos para sempre; com a caixa original eles ficavam **na frente da porta**, ou seja, o jogador podia pegá-los sem digitar a credencial e o portão do puzzle não existia. Cavidade + porta =_items inacessíveis até a porta abrir. |
| **D-33** | Regra empírica de orientação de Canvas World Space: **o `-Z` local do canvas é a face visível** | Descoberta por tentativa e erro. Terminal em `rotY 0` e mural em `rotY +90` renderizavam o texto **espelhado**; `rotY 180` (terminal) e `rotY -90` (mural, parede oeste) ficaram corretos. `localPosition` não é afetado pelo yaw, então a canvas pode ser girada sem reposicionar. |
| **D-34** | Mural usa **blocos empilhados**, não colunas alinhadas por espaços | A fonte dinâmica legada é **proporcional**: `TURNO   HORÁRIO    RESPONSÁVEL` colapsava e as colunas se sobrepunham. Empilhar (turno, horário, nome, crachá em linhas separadas) lê bem em qualquer resolução. |
| **D-35** | Self-tests ficam **no projeto** como `MenuItem` em `Tools/Escape Room/Self Test 1..4` | Não há como sintetizar clique de mouse via MCP. `button.onClick.Invoke()` percorre a cadeia real do UnityEvent e prova o wiring. Limitação honesta: **não** cobre a última milha, isto é, se o `EventSystem` entrega o clique com cursor travado ao `GraphicRaycaster`. |
| **D-36** | Abertura da porta do locker: `Play(1.1f, 0f, -95f)` | Bug real: os argumentos estavam trocados e a porta levava **115 segundos** para abrir (`Play(duration, delay, angle)`). Ângulo `-95` gira para fora do locker; `+95` giraria para dentro dele. |
| **D-37** | Não mexi nas 6 luzes magenta do kit na cena do usuário | `Assets/Barking_Dog/3D Free Modular Kit/Prefabs/Light_01.prefab` tem `m_Color {0.891, 0.213, 1.0}`, `intensity 1.5`, `range 6` — é a origem do glow rosa na parede oeste. É conteúdo do usuário; o bloom foi reduzido (1.5 → 0.85) para o artefato ficar menos intrusivo em vez de deletar a luz. |

| **D-45** | Teto elevado para **3,70 m** e pulo reduzido de **1,2 → 0,85** | A medição mostrou que a parede do kit tem só **3,03 m** — o teto anterior, fixado em 3,20, ficava 17 cm **acima** das paredes, e essa era a "janela" que mostrava o vazio. | **D-55** | `Column_01_Top` não tem collider no prefab — colunas agora recebem um | Verificado no arquivo do prefab: `Column_01_Top.prefab` **não tem** `BoxCollider`, ao contrário de `Wall_Simple_01` e `Door_Arch_01`. Duas consequências: o jogador **atravessava** as colunas, e raycasts de física não as enxergavam — foi exatamente por isso que uma coluna ficou "invisível" na frente da placa SAÍDA por várias iterações sem nenhum diagnóstico acusar. `Kit()` ganhou o parâmetro `ensureCollider`, que calcula um `BoxCollider` a partir do `Renderer.bounds` **antes** de aplicar a rotação (para os bounds ainda estarem alinhados aos eixos do próprio instance). |
| **D-56** | Placa `SAÍDA` movida para `z = -10,55` | Ela estava em `z = -11,15` e o `Door_Arch_01` continuava **na frente** dela num raio vindo de oeste. Causa raiz: a face real da frente do arco é `z ≈ -10,75`, e **não** `-11,25` como a profundidade de 1,00 m do mesh sugeria — o mesh do prefab é deslocado do seu pivô, então a profundidade não é simétrica em torno da origem. Como o arco tem 2,91 m contra 2,40 m da placa, ele avança 0,26 m para cada lado e, de um ponto de vista lateral, essa saliência fica mais perto ao longo do raio que o plano da placa. Resultado: o batente do arco era desenhado por cima do "Í". A placa agora fica 0,20 m à frente do arco. |
| **D-57** | Diagnóstico `Tools/Escape Room/What blocks the EXIT sign` | Casta um raio de 3 pontos de vista até o centro da placa e imprime **todo** hit ordenado por distância, marcando `<<< NA FRENTE DA PLACA` quando `distance < signDistance`. Usa `QueryTriggerInteraction.Collide` (a primeira versão usava `Ignore`, que torna triggers invisíveis — exatamente o buraco por onde o occluder passou) e imprime o path completo da hierarquia. Roda em **0 bloqueadores** nos 3 pontos de vista. |

| **D-58** | `EsFirstPersonCameraRig` passa a ser **dono do pitch**; para de ler `CinemachineCameraTarget` | Sintoma real do jogador: "só posso mexer a câmera da direita para a esquerda e não de cima para baixo". Causa raiz lida em `FirstPersonController.cs:132-152`: o `CameraRotation()` escreve o **pitch** em `CinemachineCameraTarget.transform.localRotation` (linha 147) e o **yaw** em `transform.Rotate` na **cápsula** (linha 150) — dois alvos diferentes. O rig apontava para um pivô que eu mesmo havia criado (`CameraTarget`), enquanto o campo do controller já vinha apontado do prefab para `PlayerCameraRoot` (que tem rotação base de **88,9°** em X). Resultado: o pitch ia para um objeto que ninguém lia, e o yaw funcionava — exatamente o padrão "um eixo sim, o outro não". Ligar a câmera a um pivô cujo dono é um script de terceiros é frágil por construção. O rig agora lê `Mouse.current.delta` ele mesmo, compõe `yaw = corpo.eulerAngles.y` com o pitch próprio, e **nunca** lê o pivô — assim não tem como dessincronizar do que o controller estiver movendo. Evidência: `Tools/Escape Room/What is under the crosshair` reporta `rig body=PlayerCapsule ... mouse=ok` e o `fwd` da câmera passou a acompanhar o yaw do corpo. |

   canvas define o tamanho de um pixel no mundo, então um alvo de canvas encolhe com a distância
   sem exceção. Por isso o painel se **chega perto**: os sockets 3D são fáceis porque são colliders
   pegos por proximity, e um painel de parede não é.
12. **O prompt não existe mais, e a barra preta também** (D-92). A placa do prompt antigo
    **sobreviveu** à remoção do prompt — bug meu, por apagar a construção e o loop de destruição
    juntos; apagar o *tipo* do componente não remove o GameObject da cena salva. A limpeza agora é
    por nome e o Self Test 6 conta os órfãos e exige zero. A crosshair em si continua
    (`F1` alterna, some quando o cursor é destravado, canvas sem `GraphicRaycaster`).
13. Gravar o screencast de 5 min. **Maximizar a Game view antes**: com a view em `1920x1080` o
   botão de reboot mede `652,7 x 159,9 px` a 2 m, contra `164,6 x 45,5 px` numa view docked de

## 7. Riscos e pendências conhecidas

1. **Duas integrações MCP no mesmo projeto.** O `com.unity.ai.assistant` sobe o relay
   nativo do Unity (portas 9001/9002, log em `Logs/relay.txt`) e o CoplayDev usa a 6400.
   Não conflitam, mas existem **duas janelas MCP** no menu Window. Se algo se comportar
   estranho, verificar qual é qual.
2. ~~**Clique com cursor travado é o ponto mais frágil do fluxo — e NÃO foi testado.**~~
   **RESOLVIDO, e levou dois passos.** O suspect registrado aqui (`Cursor.lockState`) estava
   errado. A **primeira** causa era o `worldCamera` **nulo** das Canvas World Space (D-62):
   sem ele, `GraphicRaycaster.eventCamera` devolve null e o raycast entra no ramo de Screen
   Space Overlay, comparando pixels de tela com cantos de retângulo em espaço de mundo — o
   resultado é sempre vazio e **não gera erro nenhum**. A **segunda** causa só apareceu depois
   que a primeira foi consertada, e o console continuava limpo: com o cursor travado o Input
   System reporta a posição do SO, que numa Game view docked fica **fora** do painel
   (medido em `(-1496, 396)` numa view de `659x272`), então o hit-test acontecia em um ponto
   que nem estava na tela e o clique era descartado em silêncio (D-65). Agrava: o botão
   projetava para **4,6 px** de altura, o que é inclicável de qualquer jeito (D-66). Os três
   estão corrigidos, e o `Self Test 5` agora fecha a última milha de forma automatizada
   (D-67). O que resta é o clique com um mouse físico.
3. **`MissingReferenceException` de `AudioSource` derrubava o reboot inteiro** (D-64). O
   projeto tem domain reload desativado, os estáticos de `EsAudio` sobreviviam entre sessões
   e a protection `if (_pool == null)` não detectava elementos destruídos. Como
   `ForceReboot()` tocava som **antes** de iniciar a corrotina, a exceção abortava o método e
   o botão não fazia nada. Vale notar: a exceção **subia a pilha dentro do handler do
   `onClick`**, então o sintoma era "botão morto" e não "erro de áudio" — a leitura ingenua
   do sintoma apontaria para o botão, não para o áudio.
3. **Luzes magenta do kit** (D-37): 6 instâncias de `Light_01` do Barking_Dog, cor
   `(0.89, 0.21, 1.00)`, `intensity 1.5`, `range 6`. Deixadas intactas por serem conteúdo
   do usuário; o bloom foi reduzido (1.5 → 0.85) para o artefato ficar menos intrusivo.
   Se incomodar na gravação, desative as 6 ou troque a cor no prefab.
4. **Cursor preso.** Se o jogador travar o mouse dentro da Canvas, `Esc` libera. Precisa
   ser testado na gravação.
5. **`trabalho_marqueto.unity` tem 110 objetos** criados pelo usuário. Nada foi removido
   nem reposicionado — o set novo é **adicionado** ao redor. Únicas exceções, ambas
   documentadas: o `Player` foi movido para o centro da sala (`1.5, 0.05, 0.5`) e o
   `Directional Light` foi baixado para `intensity 0.10` (é um interior). O
   `Player/PlayerFollowCamera` foi **desativado**, não removido — reative-o e remova o
   `EsFirstPersonCameraRig` para voltar ao rig original.
6. O `Plane` da cena está **desativado** (`activeSelf: false`) desde antes; mantido assim.
7. `Assets/EscapeRoom/Audio/generate_audio.py` fica versionado de propósito: é a fonte
   dos 11 clipes e permite regerá-los com `uv run --python 3.12 <script>`.
